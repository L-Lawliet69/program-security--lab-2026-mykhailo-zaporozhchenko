## 1. Purpose (Призначення та цілі безпеки)

Ця Політика безпеки встановлює обов'язкові правила, інженерні обмеження та процеси безпечної розробки для десктопної багатокористувацької гри **«Freekick»** (дуель 1 на 1 у форматі серії післяматчевих пенальті з аніме-персонажами на платформі PC / Windows).

Проект розробляється як **любительська гра для особистого користування та спільних матчів з друзями** в рамках лабораторної роботи з навчальної дисципліни **«Безпека програм та даних» (Program Security Lab 2026)**.

### 1.1. Головні цілі політики:
1. **Захист облікових даних:** гарантування неможливості компрометації автентифікаційних даних гравців (паролів) шляхом використання сучасного криптографічного хешування з унікальною сіллю.
2. **Захист від нечесної гри та сніфінгу мережевого трафіку (Anti-Sniffing):** унеможливлення перехоплення вибору напрямку удару суперника через мережеві аналізатори (Wireshark) шляхом впровадження механізму прихованого вводу ходів (Commit-Reveal).
3. **Захист цілісності збережень та статистики (Data Integrity):** запобігання несанкціонованій модифікації локальних файлів збережень (`save.json` / SQLite) у текстових редакторах (`Notepad.exe`) через використання геш-підписів HMAC-SHA256.
4. **Криптографічна чесність жеребкування:** забезпечення абсолютно рівноймовірного та непередбачуваного визначення права першого удару за допомогою криптографічно стійкого генератора випадкових чисел (CSPRNG).
5. **Мінімалізм та відповідність масштабу:** відмова від надлишкових комерційних enterprise-рішень (важких хмарних систем, WAF, зовнішніх платіжних шлюзів) на користь надійного, перевіреного та самодостатнього коду на C# у рушії Unity.

## 2. Scope (Область застосування та межі системи)

Політика поширюється на всі складові частини проекту **Freekick**:
- **Вихідний код на C#:** усі скрипти в директорії `Assets/Scripts/` (`Core`, `Managers`, `Identity`, `Character`, `Leaderboard`, `Network`, `Security`).
- **Мережева взаємодія 1v1:** сокетний протокол обміну пакетами між клієнтами гравців (режим Host-Authoritative через LAN, прямий IP або код кімнати).
- **Локальні сховища даних:** файли профілів, налаштувань та статистики дуелей у системній директорії `Application.persistentDataPath` (`%USERPROFILE%/AppData/LocalLow/Freekick/`).
- **Автоматизовані тести:** набори юніт- та інтеграційних тестів у `Tests/Editor/` та `Tests/Runtime/`.
- **Проектна документація та репозиторій:** конфігурація Git, правила гілкування, файли Markdown у каталозі `docs/`.

### Явні виключення зі скоупу (Out of Scope):
- Захист ядра операційної системи Windows та фізична безпека комп'ютерів гравців.
- Захист від модифікації оперативної пам'яті спеціалізованими інструментами рівня Ring-0 / Cheat Engine (оскільки гра створюється виключно для дружніх матчів без комерційного призового фонду).
- Внутрішня інфраструктура сторонніх віртуальних мереж (Radmin VPN, Hamachi), які користувачі можуть використовувати для встановлення прямого з'єднання.
- Хмарні корпоративні сервери та бази даних, оскільки гра працює за локальною клієнт-серверною топологією без централізованого бекенду.

## 4. Security Principles (Фундаментальні принципи безпеки)

Проект базується на таких обов'язкових безпекових принципах:
1. **Least Privilege (Мінімальні привілеї):** клієнт другого гравця не має прав самостійно призначати рахунок або змінювати стан гри. Всі критичні рішення (фіксація голів, зміна раундів, завершення матчу) приймає виключно хост-авторитет (`Host-Authoritative`).
2. **Secure by Default (Безпека за замовчуванням):** при створенні нового акаунта або збереження автоматично генерується індивідуальна сіль для пароля та розраховується HMAC-SHA256 підпис. Невалідовані пакети або пошкоджені файли збереження відхиляються за замовчуванням.
3. **Fail Securely (Безпечна відмова):** при виявленні невідповідності контрольної суми HMAC-SHA256 у файлі `save.json` гра не запускається з модифікованими даними, а безпечно повідомляє гравця про пошкодження збереження та пропонує скинути статистику до початкового стану.
4. **Defense in Depth (Багаторівневий захист):** захист від підглядання ходів забезпечується як на рівні логіки (приховування стану до фіксації обох виборів), так і на рівні мережі (нерозкриття вибору в мережевих пакетах).
5. **Commit-Reveal Mechanism:** заміна простої синхронної передачі ходу на асинхронну модель «фіксація — підтвердження — одночасне розкриття», що повністю нівелює можливість підглядання в Wireshark.
6. **No Secrets in Source Code (Відсутність секретів у репозиторії):** у репозиторій заборонено комітити робочі приватні ключі, токени чи паролі у відкритому вигляді. Контрольні солі та ключі конфігуруються через локальні файли або генеруються при першому запуску додатка.

## 5. Secure Development Environment (Безпечне середовище розробки)

1. **Контроль версій та Git:**
   - Репозиторій розміщується на сервісі GitHub.
   - Основна гілка `main` містить лише перевірений, стабільний код.
   - Прямі коміти критичних змін без тестування заборонені; розробка ведеться через функціональні гілки або локальні рев'ю.
   - Обов'язкове використання структурованого файлу `.gitignore` для запобігання потраплянню у репозиторій тимчасових файлів Unity (`Library/`, `Temp/`, `Obj/`, `Build/`, `UserSettings/`, `.vs/`).
2. **Інструментарій розробки:**
   - Unity версії 2022.3 LTS або Unity 6 LTS.
   - Мова програмування C# 10+ з увімкненим аналізом безпеки посилань (Nullable Reference Types).
   - Інструменти статичного аналізу: Roslyn Analyzers, вбудовані лінтери Visual Studio / Rider для контролю винятків та безпеки типів.
3. **Управління зовнішніми залежностями:**
   - Дозволено використання лише перевірених системних бібліотек .NET (`System.Security.Cryptography`) та офіційних пакетів Unity.
   - Заборонено підключення непроперевірених сторонніх DLL-бібліотек сумнівного походження з інтернету.

## 6. Software Protection (Захист коду, артефактів та цілісності даних)

1. **Захист файлів локальних збережень (Data Integrity):**
   - Файл збережень `save.json` та/або база SQLite розміщуються у ізольованій користувацькій директорії Windows `%LOCALAPPDATA%Low/Freekick/`.
   - До кожного збереження додається криптографічний хеш-підпис **HMAC-SHA256**, що обчислюється на основі всього вмісту даних та внутрішнього ключа додатка.
   - Будь-яка спроба відредагувати кількість перемог, нічиїх, забитих голів або нарахувати собі очки через `Notepad.exe` призводить до розбіжності HMAC і блокування завантаження невалідного сейву.
2. **Захист мережевого трафіку між друзями:**
   - Пакет вибору напрямку `SubmitDirection` містить лише ID гравця та закодований напрямок (`Left = 0, Center = 1, Right = 2`).
   - Гравець-хост не ретранслює отриманий пакет стрільця гравцю-воротарю. Інформація зберігається у внутрішній пам'яті хоста до моменту надходження вибору від обох гравців або вичерпання таймера (10 секунд).
3. **Збірка та релізи (Release Artifacts):**
   - Релізні білди компілюються під архітектуру Windows x64.
   - У фінальну збірку не включаються налагоджувальні інструменти розробника, дебаг-панелі та тестові сцени.
   - Усі помилки користувацького інтерфейсу відображаються у зручному вигляді без розкриття внутрішніх трейсів стека викликів чи шляхів до вихідного коду.

## 7. Secure Implementation (Безпечна програмна реалізація)

### 7.1. Автентифікація та зберігання паролів (`AuthService`)
- Паролі **НІКОЛИ** не зберігаються у відкритому вигляді (Plaintext).
- Використовується сучасний алгоритм криптографічного хешування:
  - **Argon2id** (рекомендовано) або **PBKDF2** (`Rfc2898DeriveBytes`) із використанням HMAC-SHA256 та кількістю ітерацій не менше 100 000.
  - Для кожного облікового запису генерується унікальна криптографічно випадкова сіль довжиною не менше 16 байт (`CSPRNG`).
- Мінімальна довжина пароля становить 8 символів.

### 7.2. Валідація вхідних даних
- **Нікнейм:** перевіряється регулярним виразом `^[a-zA-Z0-9_-]{3,20}$`. Спеціальні символи, пробіли, керуючі послідовності та HTML/SQL-теги суворо відхиляються.
- **Регістронезалежність нікнеймів:** перевірка унікальності проводиться у нижньому регістрі (`nickname.ToLowerInvariant()`), що унеможливлює створення клонів облікових записів (`Player` та `player` вважаються ідентичними).
- **Напрямки удару та стрибка:** вхідні значення строго типізовані переліком `Direction` (0, 1, 2). Будь-які значення поза допустимим діапазоном ігноруються або призводять до відхилення пакету.

### 7.3. Криптографічне жеребкування черги ударів
- Жеребкування черги першого удару перед початком матчу здійснюється виключно за допомогою класу `System.Security.Cryptography.RandomNumberGenerator` (`CSPRNG`).
- Використання генератора `System.Random` для безпекових та ігрових рішень, де потрібна непередбачуваність, категорично **заборонено**.

### 7.4. Безпечна робота з базою даних SQLite та JSON
- При використанні локальної бази даних SQLite всі SQL-запити формуються виключно через параметризовані команди (`SqliteParameter`), що повністю виключає можливість SQL-ін'єкцій.
- При серіалізації/десеріалізації JSON використовуються стандартні засоби Unity (`JsonUtility`) або `System.Text.Json` без дозволу на виконання довільного коду під час парсингу типів.

### 7.5. Журналювання (Logging)
- Заборонено виводити паролі, секретні ключі HMAC або персональні адреси електронної пошти у консоль Unity (`Debug.Log`) чи у файл `Player.log`.

## 8. Security Verification (Верифікація безпеки та тестування)

Виконання вимог безпеки перевіряється за допомогою набору автоматизованих тестів у Unity Test Framework (NUnit):

1. **EditMode тести (`Tests/Editor/`):**
   - `PasswordHashingTests`: перевірка того, що однаковий пароль для двох різних реєстрацій дає різні хеші завдяки унікальній солі; перевірка успішної валідації правильного пароля та відхилення неправильного.
   - `SaveIntegrityTests`: генерація коректного файлу збереження, валідація HMAC-підпису; модифікація одного байта у збереженні (імітація редагування в `Notepad.exe`) та верифікація того, що система фіксує невідповідність підпису і відхиляє файл.
   - `PenaltyEngineTests`: перевірка чесності механіки: збіг напрямків (`shot == dive`) завжди дає `Saved`, розбіжність (`shot != dive`) завжди дає `Goal`.
   - `CsprngFairnessTests`: статистична перевірка рівноймовірності жеребкування черги першого удару (розподіл близький до 50/50).
   - `MandatoryRoundsTests`: перевірка того, що матч не завершується після 3-го чи 4-го раунду, а завжди триває рівно 5 обов'язкових раундів (10 ударів) для обох гравців.
2. **PlayMode / Інтеграційні тести (`Tests/Runtime/`):**
   - Перевірка життєвого циклу збереження профілю та статистики дуелей.
   - Тестування відсутності збоїв при отриманні некоректних вхідних пакетів.
3. **Ручне тестування та перевірка коду (Code Review):**
   - Кожна зміна в підсистемах `Identity`, `Network` та `Security` проходить перевірку автором проекту перед включенням до основного репозиторію.

## 9. Vulnerability Management (Управління вразливостями та інцидентами)

1. **Виявлення проблем безпеки:**
   - Проблеми виявляються під час написання автотестів, самостійного тестування, відгуків друзів під час спільних матчів або зауважень викладача під час перевірки лабораторної роботи.
2. **Класифікація критичності:**
   - **Критична (Critical):** можливість обходу перевірки пароля, розкриття ходу суперника в мережі до моменту відкриття (злам Commit-Reveal), обхід перевірки HMAC-підпису збережень.
   - **Висока (High):** зависання хоста через некоректний пакет клієнта, неперевірені вхідні дані нікнейму.
   - **Середня (Medium):** некоректне оновлення статистики при раптовому розриві мережевого з'єднання.
   - **Низька (Low):** візуальні дефекти віджета профілю або табло.
3. **Порядок усунення:**
   - Критичні вразливості усуваються негайно з блокуванням релізу до проходження регресійних тестів.
   - При усуненні вразливості обов'язково пишеться юніт-тест, що відтворює проблему та підтверджує її виправлення.

## 10. Privacy Policy (Політика конфіденційності та захист даних)

Повні та вичерпні правила збору, обробки та зберігання персональних даних користувачів викладені в окремому документі:
📄 [**Політика конфіденційності Freekick (docs/privacy_policy.md)**](docs/privacy_policy.md).

### Ключові положення:
1. **Мінімізація даних:** гра збирає лише мінімально необхідні для автентифікації та геймплею дані: нікнейм, адресу електронної пошти, криптографічний хеш пароля з сіллю, ID обраного аніме-персонажа та ігрову статистику (перемоги, нічиї, голи).
2. **Локальне зберігання:** усі облікові дані зберігаються виключно на локальному пристрої користувача. Гра не передає жодних персональних даних на сторонні хмарні сервери чи рекламні мережі.
3. **Відсутність телеметрії:** у додатку відсутні трекери, системи аналітики та приховані модулі збору даних.
4. **Право на видалення:** користувач у будь-який момент може повністю видалити свій профіль та історію матчів, видаливши локальний файл збереження або скориставшись кнопкою скидання у налаштуваннях гри.

## 11. Exceptions (Порядок надання винятків)

1. Відступ від положень цієї політики допускається лише для локальних налагоджувальних збірок (Debug Mode), наприклад:
   - Тимчасовий запуск гри без обов'язкового підключення мережевого клієнта (режим тренування з локальним ботом).
   - Логування технічних параметрів мережевих пакетів для діагностики з'єднання.
2. Будь-які налагоджувальні винятки суворо заборонено переносити в основну гілку `main` або включати у фінальні збірки гри, призначені для демонстрації лабораторної роботи.
