> Ця політика визначає інженерні, архітектурні та безпекові вимоги до проекту **«Freekick»** — любительської десктопної онлайн-гри під платформу **PC (Windows)**, розробленої на типовому ігровому рушії **Unity (C#)**. Проект створюється для особистого користування та спільних матчів з друзями по мережі, а також для демонстрації практичних навичок у рамках лабораторної роботи з дисципліни **«Безпека програм та даних» (Program Security Lab 2026)**.
>
> **Межі скоупу:** Проект є симулятором дуелі післяматчевих пенальті 1v1 з аніме-персонажами («Blue Lock», «Captain Tsubasa», «Inazuma Eleven» тощо). Включає реєстрацію та профіль користувача у правому верхньому куті, вибір героя з каталогу, серію з 5 обов'язкових раундів (10 ударів сумарно), вибір 3 напрямків (`LEFT`, `CENTER`, `RIGHT`), розрахунок голів/сейвів, підтримку нічиєї (`DRAW`), прихований ввід ходів (захист від сніфінгу) та ведення статистики дуелей між друзями. Гра **НЕ** використовує важких комерційних хмарних мікросервісів, зовнішніх платежів чи донату.

## 1. Загальні правила та принципи любительської розробки

1. **Орієнтація на особисте користування з друзями:**
   - Мережева гра організована за простою і надійною моделлю: один із гравців виступає хостом (Host/Server), а інший підключається як клієнт (Client) через локальну мережу (LAN), прямий IP, віртуальну мережу (Radmin VPN / Hamachi) або через легкий лобі-сервер.
   - Відсутність потреби у складній серверній інфраструктурі, балансувальниках навантаження чи дорогих хмарних базах даних.
2. **Типовий ігровий рушій (Unity / C#):**
   - Розробка ведеться на рушії Unity з використанням мови C#.
   - Використовується зрозуміла, чиста об'єктно-орієнтована архітектура (ООП) без надмірного корпоративного оверінжинірингу.
3. **Безпека на рівні лабораторної роботи:**
   - Оскільки проект виконується в рамках курсу з безпеки програмного забезпечення, обов'язково реалізуються ключові захисні механізми:
     - Надійне криптографічне хешування паролів (Argon2id або PBKDF2 з сіллю).
     - Криптографічно стійке жеребкування черги ударів (CSPRNG).
     - Захист від мережевого сніфінгу ходів через прихований одночасний ввід (Commit-Reveal на хості).
     - Захист файлів збережень та статистики від ручної підробки в блокноті через перевірочний підпис цілісності (HMAC-SHA256).

## 2. Технологічний стек та інструментарій

- **Ігровий рушій:** Unity 2022.3 LTS (або Unity 6 LTS), збірка під **PC Standalone (Windows x64)**.
- **Мова програмування:** **C# 10+** (.NET Standard 2.1 / .NET 8).
- **Керування введенням:** Unity New Input System або класичний Input Manager (підтримка клавіш `A / W / D`, стрілок `← / ↑ / →` або кліків миші по інтерактивних зонах воріт).
- **Мережева взаємодія для друзів (Networking):**
   - Unity Netcode for GameObjects, Mirror або простий сокетний C# TCP/WebSocket клієнт-сервер.
   - Модель хоста-авторитета (Host-Authoritative): гравець-хост або локальний сервер контролює таймер ходу, отримує приховані вибори обох сторін і одночасно оприлюднює результат.
- **Збереження даних:**
   - Локальний файл у форматі JSON або вбудована база даних SQLite у каталозі `Application.persistentDataPath` (шлях у Windows: `%USERPROFILE%/AppData/LocalLow/Freekick/`).
   - Захист цілісності: додавання HMAC-SHA256 контрольного підпису до файлу збереження для захисту від банальної підміни рахунку чи статистики в текстовому редакторі.
- **Криптографія:**
   - Стандартні криптографічні класи .NET (`System.Security.Cryptography`): `RandomNumberGenerator` для CSPRNG, `HMACSHA256` для цілісності, `Rfc2898DeriveBytes` (PBKDF2) або бібліотека Konscious.Security.Cryptography для Argon2id.

## 3. Структура Unity-проекту (C#)

Проект має типову модульну структуру стандартного проекту Unity для ПК:

```

│   │   ├── MatchSession.cs            # Дані та перебіг поточної гри (раунди, рахунок)

│   │   └── PlayerData.cs              # Модель гравця та активного персонажа
│   ├── Managers/                      # Контролери життєвого циклу гри (MonoBehaviour)
│   │   ├── GameManager.cs             # Головний координатор ігрових станів
│   │   ├── MatchController.cs         # Керування покроковим процесом 10 ударів
│   │   └── UIManager.cs               # Прив'язка даних до інтерфейсу користувача
│   ├── Identity/                      # Облікові записи та профіль
│   │   ├── AuthService.cs             # Реєстрація, перевірка унікальності нікнейму, вхід
│   │   └── UserProfile.cs             # Дані профілю гравця та активного аватара
│   ├── Character/                     # Каталог аніме-персонажів
│   │   ├── CharacterData.cs           # ScriptableObject або клас опису персонажа
│   │   ├── TitleData.cs               # Дані аніме-тайтлу («Blue Lock», «Captain Tsubasa» тощо)

│       └── CryptoRandom.cs            # Безпечне CSPRNG жеребкування першого удару
├── Resources/ або ScriptableObjects/  # Ігрові ресурси, спрайти героїв, префаби воріт
├── Scenes/                            # Сцени: MenuScene, MatchScene, LeaderboardScene
└── Tests/                             # Автоматизовані тести для лаби
```

## 4. Стандарти кодування на C#

1. **Іменування:**
   - `PascalCase` для імен класів, структур, інтерфейсів, методів та публічних властивостей (`PenaltyEngine`, `ResolveShot()`, `CurrentScore`).
   - `camelCase` для параметрів методів та локальних змінних (`shotDirection`, `playerScore`).
   - `_camelCase` для приватних полів класу (`_activeCharacter`, `_currentRound`).
   - Префікс `I` для інтерфейсів (`ISaveService`, `INetworkService`).
2. **Розділення обов'язків:**
   - Чиста ігрова логіка (розрахунок переможця, правила 5 обов'язкових раундів, порівняння напрямків) реалізується у чистих C# класах без спадкування від `MonoBehaviour`. Це забезпечує легке юніт-тестування без необхідності запускати Unity Engine.
   - Класи `MonoBehaviour` відповідають лише за відображення (UI, анімації персонажів, відтворення аудіо ударів, перехоплення кліків).
3. **Безпека посилань (Null-Safety):**
   - Використання можливостей C# Nullable Reference Types (`string?`, `?.`, `??`).
   - Замість повернення `null` для списків чи колекцій повертати порожні масиви (`Array.Empty<T>()` або `new List<T>()`).
4. **Продуктивність на ПК:**
   - Не викликати важкі методи пошуку (`GetComponent()`, `FindObjectOfType()`) у щокадровому методі `Update()`. Усі необхідні компоненти кешуються в `Awake()` або `Start()`.

## 5. Політика безпеки даних для лабораторної роботи

1. **Хешування паролів:**
   - Паролі зберігаються виключно у вигляді криптографічного хешу з індивідуальною сіллю.
   - Заборонено зберігати паролі у відкритому вигляді або використовувати застарілі алгоритми (MD5, SHA-1).
2. **Захист від сніфінгу мережевого трафіку (Anti-Sniffing Commit-Reveal):**
   - У дуелі 1v1 хост отримує вибір стрільця та воротаря асинхронно і зберігає їх приховано.
   - Жоден гравець не отримує інформацію про хід опонента доти, доки обидва гравці не зроблять свій вибір або не вичерпається таймер ходу (10 секунд).
3. **Цілісність файлу збереження (Data Integrity):**
   - Файл збереження `save.json` або база SQLite містить контрольну суму HMAC-SHA256, що генерується на основі внутрішнього секретного ключа додатка.
   - При спробі відредагувати кількість перемог чи забитих голів у звичайному `Notepad.exe` підпис стає недійсним, і гра сигналізує про пошкодження файлу або скидає невалідні значення.
4. **Валідація вхідних даних:**
   - Перевірка нікнеймів за регулярним виразом `^[a-zA-Z0-9_-]{3,20}$`.
   - Запобігання створенню дублікатів нікнеймів без урахування регістру (`admin` та `Admin` вважаються однаковими).
   - Екранування або параметризація запитів до бази SQLite для запобігання SQL-ін'єкціям.

## 6. Політика тестування

Для здачі лабораторної роботи готуються набори автоматичних тестів (Unity Test Framework / NUnit):
1. **EditMode тести (`Tests/Editor/`):**
   - Перевірка механіки удару: однаковий напрямок $\rightarrow$ сейв; різний $\rightarrow$ гол.
   - Перевірка обов'язковості 10 ударів: гра не повинна завершуватися після 3-го або 4-го раунду.
   - Перевірка жеребкування CSPRNG: генерація рівномірного розподілу першого удару.
   - Перевірка розрахунку результату нічиєї (`DRAW`): при 2:2 або 3:3 призначається нічия і нараховується по +1 очку.
   - Перевірка HMAC-підпису: валідація коректного сейву та детекція підробленого файлу.
2. **PlayMode / Інтеграційні тести (`Tests/Runtime/`):**
   - Перевірка збереження та завантаження локального профілю.
   - Перевірка коректності оновлення UI віджета профілю у правому верхньому куті.

## 7. Git Workflow

- **Гілки:**
  - `main` — стабільна протестована версія гри.
  - `develop` — гілка поточної розробки та інтеграції.
  - `feature/<назва>` — гілки під окремі функції.
- **Файл `.gitignore`:**
  - Обов'язкове ігнорування службових папок Unity (`Library/`, `Temp/`, `Obj/`, `Build/`, `UserSettings/`).
- **Префікси повідомлень коммітів:**
  - `[CORE]` — логіка пенальті, правила, розрахунок голів.
  - `[UI]` — меню, віджет профілю, екран матчу, таблиця лідерів.
  - `[NET]` — мережевий обмін для гри з друзями, пакети, Commit-Reveal.
  - `[SEC]` — хешування паролів, перевірка цілісності HMAC, CSPRNG.
  - `[DOCS]` — оновлення документації.
  - `[TEST]` — додавання та оновлення тестів.

## 8. Анти-патерни та неприпустимі практики

1. **Клієнтський розрахунок результату удару:** Розрахунок голу/сейву на стороні гравця-стрільця неприпустимий — результат завжди визначається на хості/сервері.
2. **Передчасне завершення матчу:** Зупинка гри після 3-го або 4-го раунду за наявності математичної переваги порушує інваріант збору повної статистики забитих/пропущених м'ячів.
3. **Відкрита трансляція ходу до завершення раунду:** Надсилання вибору снайпера на клієнт воротаря до моменту, коли воротар зробив свій вибір, створює пряму вразливість перед сніфінгом пакетів.
4. **Збереження паролів у відкритому вигляді:** Збереження паролів у відкритому тексті або MD5 є неприпустимим порушенням вимог безпеки.
5. **Важкі операції у щокадровому методі `Update()`:** Виклики `GetComponent()` або `GameObject.Find()` всередині `Update()`.
