> Ця політика визначає обов'язкові інженерні, архітектурні та безпекові вимоги до коду проекту **«Freekick»** — багатокористувацької онлайн-гри в жанрі футбольної дуелі (серія післяматчевих пенальті 1v1) з вибором аніме-персонажів із популярних франшиз, системою глобального рейтингу та суворими механізмами захисту облікових даних і цілісності ігрового стану.
>
> **Межі скоупу:** Проект фокусується на онлайн-дуелях 1v1 (по 5 ударів у кожного гравця з гарантованим пробиттям усіх ударів для точного збору статистики), авторизації користувачів, автентифікації з криптографічним хешуванням, каталозі аніме-персонажів та підрахунку глобальної таблиці лідерів. Проект **НЕ** включає симуляцію повноцінного 90-хвилинного футбольного матчу з 11 польовими гравцями, а також не реалізує внутрішньоігрові фінансові мікротранзакції за реальні гроші.

## 1. Скоуп

Ця політика поширюється на всі складові програмного комплексу **Freekick** — на серверний код (`src/Backend/`), клієнтський додаток (`src/Frontend/` або настільний клієнт), шар даних, а також на повний комплект модульних, інтеграційних та безпекових тестів (`tests/`). Вона є обов'язковою для виконання всіма розробниками, інженерами з безпеки та автоматизованими асистентами.

## 2. Технологічний стек та інструментарій

- **Мова бекенду:** PHP 8.3+ (або C# .NET 8 / TypeScript Node.js у залежності від рантайму ігрового шлюзу) зі строгою типізацією `declare(strict_types=1);`.
- **Архітектурний підхід:** Domain-Driven Design (DDD), Hexagonal Architecture (Ports & Adapters), CQRS.
- **База даних:** PostgreSQL 16+ для збереження облікових записів, профілів, статистики та каталогу персонажів.
- **In-Memory Store & Realtime Engine:** Redis 7+ для швидкого маткінгу (Matchmaking Queue), зберігання активних станів ігрових сесій та синхронізації таймаутів раундів.
- **Транспорт реального часу:** WebSockets (WSS) з обов'язковим TLS 1.3 для передачі ходів гри.
- **Менеджер залежностей:** Composer / npm.
- **Статичний аналіз:** PHPStan (рівень 8 або max), Deptrac для контролю меж шарів.
- **Форматування / Code Style:** PSR-12, Laravel Pint / PHP-CS-Fixer.
- **Тестові фреймворки:** PHPUnit 11+, Pest, розширення для криптографічного тестування.
- **Контроль версій:** Git.

## 3. Фундаментальні принципи розробки

- **Server-Authoritative Game State (Абсолютний авторитет сервера).** Клієнтський додаток є лише візуалізатором стану (View) та інтерфейсом вводу. Жодне ігрове рішення (гол, сейв, визначення переможця, вибір черги) не приймається на боці клієнта. Будь-які маніпуляції з клієнтським кодом не можуть призвести до спотворення результату.
- **Zero Trust до клієнтського вводу.** Будь-які вхідні дані (нікнейми, пошта, паролі, вибір напрямку удару) проходять сувору валідацію на стороні сервера.
- **Чисте розділення шарів (Layer Separation).** Інфраструктурний код (WebSockets, SQL, Redis, криптографічні бібліотеки) не проникає у доменну модель. Домен залежить лише від абстрактних контрактів.
- **DDD для бізнес-правил.** Правила матчу, черговість ударів, обов'язковість завершення всіх 5 ударів та оновлення статистики реалізуються виключно в межах агрегатів та доменних сутностей.
- **Криптографічна надійність за замовчуванням (Security by Design).** Паролі ніколи не зберігаються у відкритому чи оборотно зашифрованому вигляді; токени мають обмежений час життя; рандомізація базується на CSPRNG.
- **Непорушність політики.** Жодні вимоги терміновості релізу не виправдовують компрометацію безпеки чи відхилення від політики.

## 4. Архітектура та структура системи

Проект будується за шаровою архітектурою з ізоляцією залежностей (виклики спрямовані ззовні всередину):

```
Presentation / WebSocket Layer
          ↓
   Application Layer (Use Cases, Commands, Queries)
          ↓
      Domain Layer (Entities, VO, Policies, Domain Services)
          ↑ [Inversion of Control via Contracts]
   Infrastructure Layer (Persistence, Cryptography, Network, Redis)
```

## 5. Політика безпеки та криптографічного захисту

Оскільки даний проект виконується в рамках лабораторної роботи з дисципліни **«Безпека програм та даних»**, до системи висуваються спеціальні вимоги безпеки:

### 5.1. Зберігання та обробка паролів
- **Алгоритм:** Тільки **Argon2id** (відповідає рекомендаціям NIST SP 800-63B та OWASP Password Storage Cheat Sheet).
- **Параметри:** Memory cost $\ge 65536$ KiB (64 MiB), Time cost $\ge 3$ ітерації, Parallelism = 1 потік.
- **Заборона:** Категорично заборонено використання MD5, SHA-1, SHA-256 без солі, DES або оборотного шифрування для паролів.
- **Вимоги до паролів:** Мінімум 8 символів, містить принаймні одну велику літеру, одну малу літеру, одну цифру та один спецсимвол (`PasswordComplexityDPolicy`).

### 5.2. Унікальність ідентифікаторів та публічних імен
- **Нікнейм:** Унікальний у межах всієї системи без урахування регістру (`unique index LOWER(nickname)`).
- **Валідація нікнейма:** Формат `^[a-zA-Z0-9_-]{3,20}$`. Заборонено використання символів HTML/JS/SQL для запобігання XSS та SQL Injection.

### 5.3. Захист передачі даних та сесій
- Усі мережеві комунікації здійснюються виключно через **TLS 1.3** (HTTPS / WSS).
- Автентифікація WebSocket-з'єднання базується на короткоживучих криптографічних токенах (JWT Access Token із підписом Ed25519 або HMAC-SHA256, термін життя $\le 15$ хвилин) з використанням Refresh Token у захищених `HttpOnly, Secure, SameSite=Strict` cookies.

### 5.4. Захист ігрової механіки від сніфінгу та маніпуляцій (Anti-Cheat / Commit-Reveal)
- У кожному ударі беруть участь Стрілець (Shooter) та Воротар (Goalkeeper).
- Обидва обирають напрямок: **LEFT**, **CENTER** або **RIGHT**.
- **Загроза:** Якщо Стрілець надішле свій вибір на сервер у відкритому сокет-повідомленні, а сервер транслює його Воротарю, Воротар зможе перехопити пакет і завжди обирати правильний сейв.
- **Рішення безпеки:** Сервер приймає вибір обох гравців **запечатаним** (Commit-Reveal або одночасний прийом ходів у межах тайм-вікна 10 секунд).
  1. Гравець А та Гравець Б надсилають свій вибір серверу незалежно.
  2. Сервер фіксує обидва вибори в захищеному стані в пам'яті (Redis).
  3. Лише після отримання виборів від ОБОХ гравців (або після вичерпання таймауту) сервер розкриває результат:
     - Якщо `direction_shot == direction_dive` $\rightarrow$ **SAVE (Відбито)**;
     - Якщо `direction_shot != direction_dive` $\rightarrow$ **GOAL (Гол)**.
- **Криптографічний жереб (Coin Toss):** Визначення того, хто б'є першим, здійснюється за допомогою криптографічно стійкого генератора псевдовипадкових чисел (CSPRNG — `random_int()` у PHP), що унеможливлює передбачення результату гравцем.

### 5.5. Захист від Brute-Force та DoS
- Реалізація механізму Rate Limiting (Leaky Bucket / Redis Sliding Window): не більше 5 невдалих спроб входу за 15 хвилин з однієї IP-адреси/акаунта.
- Обмеження кількості активних сесій на один акаунт (запобігання одночасній грі з двох місць).

## 6. Політика доменних івентів

Усі значущі зміни стану системи публікуються як типізовані доменні івенти (Domain Events, DE).

- **Структура івента:**
  - `eventId`: UUID v4.
  - `aggregateId`: UUID кореня агрегату.
  - `occurredOn`: DateTimeImmutable (UTC, мікросекунди).
  - `eventName`: рядок формату `fk.<bounded_context>.<event_name>`.
  - `payload`: типізований об'єкт даних івента (Domain Event Data, DED).

- **Реєстр ключових івентів:**
  - `fk.identity.user_registered` — реєстрація нового користувача.
  - `fk.character.active_character_changed` — зміна обраного аніме-персонажа.
  - `fk.gameplay.match_created` — створення ігрової кімнати та підбір суперників.
  - `fk.gameplay.coin_toss_completed` — завершення розіграшу черги першого удару.
  - `fk.gameplay.shot_resolved` — обчислення результату окремого пенальті (Гол/Сейв).
  - `fk.gameplay.round_completed` — завершення раунду (обидва гравці виконали по удару).
  - `fk.gameplay.match_completed` — фінал матчу після виконання всіх 5 ударів обома гравцями.
  - `fk.leaderboard.stats_updated` — синхронізація глобальної таблиці лідерів.

## 8. Політика типізації та анотацій

- Сувора типізація у кожному файлі (`declare(strict_types=1);`).
- Усі методи мають явно оголошені типи аргументів та тип повернення.
- Докблоки (`PHPDoc` / `JSDoc`) обов'язкові для всіх публічних інтерфейсів та методів.
- Докблок містить:
  - Короткий бізнес-опис мети методу (навіщо, а не що).
  - `@param` з бізнес-обмеженнями.
  - `@return` зі специфікацією стану.
  - `@throws` із переліком можливих доменних та інфраструктурних винятків.

## 9. Політика винятків та обробки помилок

Усі винятки проекту обов'язково успадковують базовий клас `AFKException` (префікс **FK** — Freekick).

### Структура коду помилки: `FK.<СЕГМЕНТ>.<ЧИСЛОВИЙ_КОД>`

| Сегмент | Призначення | Приклад коду | Приклад винятку |
|---|---|---|---|
| `AUTH` | Модуль автентифікації та профілів | `FK.AUTH.1` | `NicknameAlreadyTakenException` |
| `AUTH` | Помилка формату/складності пароля | `FK.AUTH.2` | `WeakPasswordException` |
| `AUTH` | Невірні облікові дані | `FK.AUTH.3` | `InvalidCredentialsException` |
| `CHAR` | Модуль каталогу персонажів | `FK.CHAR.1` | `CharacterNotFoundException` |
| `CHAR` | Персонаж заблокований або неактивний | `FK.CHAR.2` | `CharacterUnavailableException` |
| `GAME` | Модуль ігрового процесу | `FK.GAME.1` | `InvalidShotDirectionException` |
| `GAME` | Спроба ходу не у свою чергу | `FK.GAME.2` | `NotPlayerTurnException` |
| `GAME` | Спроба дострокового завершення гри | `FK.GAME.3` | `PrematureMatchTerminationException` |
| `GAME` | Матч уже завершено | `FK.GAME.4` | `MatchAlreadyFinishedException` |
| `LEAD` | Модуль таблиці лідерів | `FK.LEAD.1` | `LeaderboardUnavailableException` |
| `INF` | Інфраструктурні помилки (БД, мережа) | `FK.INF.1` | `DatabaseConnectionException` |
| `CORE` | Системні помилки SharedKernel | `FK.CORE.1` | `InvalidUuidException` |

**Правило безпеки:** Деталі системних помилок та стек викликів ніколи не передаються клієнту у відповідях. Клієнту віддається лише код помилки (наприклад, `FK.AUTH.1`) та безпечне людино-зрозуміле повідомлення.

## 10. NULL-less політика

- Уникати використання сирого `null` у доменній бізнес-логіці.
- Для необов'язкових посилань застосовувати патерн Null Object або типізовані Option-обгортки (наприклад, `NoCharacterRefVO` замість `null`).
- Колекції завжди повертають порожній масив або колекцію, ніколи не `null`.

## 11. Політика тестування та верифікації

- **Піраміда тестування:**
  1. **Юніт-тести (Domain):** Покриття 100% публічних методів сутностей, VO та сервісів. Перевірка інваріантів, правила обов'язкових 5 ударів, черговості та розрахунку голів.
  2. **Інтеграційні тести (Application + Infrastructure):** Робота Use Cases із тестовою БД PostgreSQL та замоканим/тестовим Redis.

     - Тести стійкості хешування Argon2id до таймінг-атак.
     - Тести ізоляції ходів (перевірка, що клієнт не може отримати хід суперника до розкриття).
     - Перевірка на ін'єкції в поля нікнеймів та електронної пошти.
- Тести запускаються без реальних зовнішніх мережевих викликів.

## 12. Git Workflow

- **Гілки:**
  - `main` — стабільна гілка з релізними версіями та перевіреною документацією.
  - `develop` — основна гілка поточної розробки.

- **Префікси повідомлень коммітів:**
  - `[DOCS]` — зміни та додавання проектної документації, специфікацій, діаграм.
  - `[DEV]` — розробка програмного коду модулів.
  - `[SEC]` — реалізація захисних механізмів, виправлення вразливостей, налаштування шифрування.
  - `[FIX]` — виправлення багів.
  - `[POLICY]` — зміна політики проекту або архітектурних правил.
  - `[TEST]` — додавання або оновлення тестового покриття.

## 14. Анти-патерни та неприпустимі практики

1. **Клієнтський розрахунок результату.** Визначення голу/сейву у веб-клієнті або додатку.
2. **Передчасний вихід із матчу за математичної перемоги.** Зупинка матчу після 3-го або 4-го раунду порушує статистику забитих та пропущених голів для глобального лідерборду.
3. **Зберігання паролів у відкритому вигляді або MD5/SHA-1.** Грубе порушення стандартів безпеки.
4. **Розкриття вибору напрямку супернику до запечатування обох ходів.** Створює вразливість перед сніфінгом та аналізом трафіку.
5. **Протікання фреймворку в Domain.** Використання ORM-моделей чи HTTP-запитів безпосередньо в доменних сутностях.
6. **Ігнорування регістру нікнеймів при реєстрації.** Допущення створення однакових імен у різному регістрі (наприклад, `Admin` та `admin`).
